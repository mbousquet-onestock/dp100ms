## Analysis

### Configuration measured

- One machine with 4 vCPUs. The server is pinned to 2 CPUs (`taskset -c 0,1`, `GOMAXPROCS=2`), comparable to a 2-vCPU Cloud Run instance. k6 is pinned to the 2 other CPUs, so the load generator does not take CPU from the server.
- Reference dataset: seed 42, 120 stock points, 12,000 SKUs, 1,200,000 stock lines, 556 legs. Data is in memory (generated at boot); PostgreSQL is not on the request path in either mode.
- Basket pool: 5,000 different baskets generated by the server from the real stock: 33% single item, 43% multi-item that one source can serve, 15% verified multi-source (no single point holds them), 9% multi-source towards a city with a consolidation hub. Order times are spread over a week (cut-offs, weekends). Requests use 1 to 4 delivery modes. Each iteration takes the next basket, so 54,000 to 58,000 requests per closed-loop scenario cycle through the pool about 11 times.
- Latency is k6's `http_req_duration`: from sending the request to the last byte of the response, including server-side JSON serialisation, over loopback with keep-alive. All requests are counted; no request failed in any scenario.

### Reading the results

- **Capacity.** The server saturates at about **1,900 req/s on 2 cores**: every closed-loop scenario from 10 VUs up runs at 91 to 93% CPU. That is about 1.05 ms of CPU per request, of which the engine accounts for about 0.6 to 0.8 ms; the rest is HTTP, JSON decoding and encoding, and GC.
- **Constant-rate scenarios (open model)** show latency below saturation: P95 is **3.4 ms at 250 req/s, 4.5 ms at 500, 12 ms at 1,000 and 39 ms at 1,500 req/s**. At 2,000 req/s the offered load exceeds capacity: 5,074 iterations were dropped by k6 and latency rises to the queueing regime (P95 683 ms). The maximum throughput that holds the target on this configuration is therefore between 1,500 and 1,900 req/s.
- **Closed-loop scenarios with zero think time** model N users each sending a new request as soon as the previous answer arrives. Above saturation, latency is set by queueing (Little's law: mean latency ≈ N / throughput):
  - 100 VUs / 1,906 req/s gives about 52 ms average, and P95 is **87.9 ms** (target met);
  - 250 VUs gives 139 ms P50 and 215 ms P95; 500 VUs and 1,000 VUs scale linearly.

  These three scenarios **do not meet the target**. The cause is the CPU limit of a 2-core instance, not a slow computation: the engine time per request stays at 2 to 4 ms in those runs. Holding P95 < 100 ms with 250 or more zero-think-time users needs more cores or more instances. For example, 1,000 such users at 100 ms need about 10,000 req/s, which is about 6 instances of this size behind a load balancer (Cloud Run does this with `--max-instances`).
- **Basket categories** have nearly identical latency. Multi-source and consolidation baskets cost almost the same as single-item ones, because the work is bounded (candidate cap, beam width, branch and bound on hubs).
- **Route cache hit rate** is above 99.9%. Only the first request for a (department, mode) pair builds its path set. Stock is never cached: every request takes a fresh snapshot.

### Optimisation history (measured during development, same machine)

| Step | Engine time / request (single thread, `make bench-go`) | End-to-end observation |
|---|---:|---|
| First complete version | 1.75 ms | about 770 req/s, P95 27 ms at 10 VUs. These numbers were also limited by k6, which parsed every JSON body and copied the basket pool into each VU. |
| Integer clock (no `time.Date` on the hot path) | 1.32 ms | |
| Coverage/distance pre-ranking of candidates, allocation-free beam scoring, packing memo, pruning slower paths | 0.93 ms | |
| Dense node indexes, hash keys instead of string signatures, canonical paths shared across modes | 0.78 ms | |
| k6: shared basket pool, metrics read from response headers, bodies discarded after full receipt | | k6 went from saturating its 2 CPUs to about 0.8 CPU; the server became the measured bottleneck |
| Branch and bound on consolidation hubs, single-pass fastest/cheapest direct planning | 0.69 ms | |
| Per-request pools for path timings, cached parcel groups | 0.63 ms | about 1,900 req/s on 2 cores (this report) |

A faster JSON encoder (`goccy/go-json`) was evaluated: it saves about 43 µs per response (about 4% of request CPU). That was not judged worth an extra dependency.

### Search quality versus latency

The bounded search is compared with a near-exhaustive one in `docs/ARCHITECTURE.md` (section 5). With the default settings, the earliest promise per mode is identical in 94.6% of cases and no mode is ever lost. Raising the beam width and the allocation count reaches 99.1% at about 2.3 times the engine cost. Both are runtime settings (`PUT /api/v1/settings`).

### Limits of this measurement

- Loopback network: Internet latency to Vercel or Cloud Run comes on top. To measure it, run `BASE_URL=https://… make benchmark` from a client machine.
- On Vercel, every cold start includes the dataset generation, and each instance has its own CPU allocation; these numbers do not transfer as-is.
- k6 and the server share one physical host (on separate CPUs). The memory bus and caches are shared.
- A built-in in-process benchmark is also available in the UI. It excludes the network and k6, so its results are not comparable with this table.

### Reproduce

```bash
make build                     # or: go build -o bin/server ./cmd/server
GOMAXPROCS=2 taskset -c 0,1 ./bin/server &          # PORT=8080 by default
K6_CPUS=2,3 SERVER_CPUS=0,1 make benchmark          # 11 scenarios × 30 s
```
